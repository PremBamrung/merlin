# Plan — Saving conversations in the Chat tab (continuable threads)

> Status: **IMPLEMENTED.** Continuable threads ship for the library-wide `/chat`
> tab; the Reader per-item chat stays ephemeral. The build follows this plan with
> **one deliberate deviation: persistence is client-driven, not server-side.**
>
> **What was built**
> - Migration `005` + `ChatThread`/`ChatMessage` models; turns stored as the
>   verbatim Vercel AI SDK `UIMessage` parts (JSON), citations included.
> - `merlin/services/chat_history.py`: `save_thread` (upsert + replace messages +
>   lazy title), `list_threads`, `get_thread`, `rename_thread`, `delete_thread`,
>   `generate_title` (best-effort, offline-safe). Title agent: `rag.agent.title_agent`.
> - Endpoints in `api/routers/chat.py`: `GET/PUT/PATCH/DELETE /api/chat/threads…`.
> - Frontend: `hooks/useChatThreads.ts`, `useAgentChat` gains `id`/`initialMessages`/
>   `onFinish`, and `routes/chat.tsx` gets a ChatGPT-style thread sidebar
>   (continuable; `?thread=<id>`; rename/delete; mobile drawer).
>
> **The deviation (§3 spike outcome).** Reading the Vercel adapter's
> `load_messages` proved the round-trip works through the *existing* transport
> (tool-call/result pairs reconstruct; custom `data-` parts are skipped) — the
> frontend already POSTs the full part list every turn. So instead of
> reconstructing parts server-side in `on_complete` (which drops our custom
> `data-citations`) + streaming `data-thread-id`/`data-thread-title`, the client
> PUTs the exact rendered turn on `onFinish` (it holds citations verbatim). The
> client generates the thread id; the title is generated synchronously in the
> first PUT (the answer has already streamed, so nothing user-facing blocks). The
> §6 wire additions and §5 Phase-2 parallel `asyncio` title task were therefore
> **not needed**. Everything else below reflects what shipped.
>
> ---
>
> Original plan (kept for context):
>
> Locked: threads are **continuable** (reopen and keep chatting with full
> context), persisted **server-side** as typed parts; titles are **generated by a
> cheap LLM call in parallel with the first turn** (never blocking the answer).
> Scope: the library-wide `/chat` tab. The Reader per-item chat stays ephemeral.

## 1. Decision

- Persist every `/chat` turn (user + assistant) to the DB as the **Vercel AI SDK
  `UIMessage` parts** (text, reasoning, tool calls, citations) so a reopened thread
  renders exactly as it did live.
- **Continuable:** reopening a thread seeds `useChat` with the stored messages; the
  next turn POSTs the full list, which the adapter already replays as agent
  history — so continuation works through the existing mechanism, *if* stored parts
  round-trip cleanly (the spike, §3).
- **Titles:** when a new thread's first turn starts, fire a cheap one-shot LLM
  "title this in ≤6 words" call **concurrently** with the agent run; persist the
  title and push it to the client. Never block streaming on it.

## 2. Current state (what changes)

Fully ephemeral by design (`AGENTIC_CHAT_PLAN.md`): `useChat` holds messages in
React state (`web/src/hooks/useAgentChat.ts`); `api/routers/chat.py` is stateless;
`merlin/db/models.py` has no thread/message tables. We add tables + a service + read
endpoints + persistence in the existing `on_complete` seam + a frontend sidebar.

## 3. SPIKE FIRST (the one real unknown)

Before building the UI, prove the **round-trip** on the pinned versions
(`pydantic-ai==1.107`, `ai@6`, `@ai-sdk/react@3`):

1. Run a chat turn; capture the assistant's emitted `UIMessage` parts (tool calls +
   `data-citations` included).
2. Persist them, reload, seed a fresh `useChat({ messages: stored })` → confirm the
   thread **renders identically** (tool chips, reasoning, Sources).
3. Send a follow-up → confirm the adapter accepts the replayed history (incl.
   tool-call/tool-result pairs) and the model **continues with context** (no
   "orphaned tool_call_id" error — the one-reply-per-`tool_call_id` invariant).

If (3) fails for tool parts, fallback: also store the Pydantic-AI history
(`VercelAIAdapter.dump_messages(...)` / `result.new_messages_json()`) and pass it
as `message_history` on continuation, using the stored UI parts only for display.
Decide which path *after* the spike. **Do not build the UI until this is settled.**

## 4. Storage — migration `005`/`006`

(`down_revision` = latest at build time; `004` today, or `005` if cost-tracking
landed first.)

```
chat_threads
  id          TEXT PK
  title       TEXT NULL              -- NULL until the parallel title call returns
  created_at  DATETIME
  updated_at  DATETIME              -- bumped per message; sidebar sorts by this

chat_messages
  id          TEXT PK
  thread_id   TEXT FK -> chat_threads(id) ON DELETE CASCADE
  seq         INTEGER               -- order within thread
  role        TEXT                  -- 'user' | 'assistant'
  parts       TEXT                  -- JSON: UIMessage parts
  created_at  DATETIME
```

Plain `op.create_table` (no FTS/triggers → autogenerate OK). Cascade-delete drops a
thread's messages. Add `ChatThread`/`ChatMessage` models to `merlin/db/models.py`.
(Optional later: an FTS table to search chat history — not v1.)

## 5. Build steps

### Phase 0 — tables + service
`merlin/services/chat_history.py`:
```python
def create_thread() -> str                              # returns thread_id, title NULL
def set_title(thread_id, title) -> None
def append_message(thread_id, role, parts) -> None      # next seq, bump updated_at
def list_threads() -> list[dict]                        # {id,title,updated_at,message_count}
def get_thread(thread_id) -> dict | None                # {id,title,messages:[{role,parts}]}
def rename_thread(thread_id, title) -> bool
def delete_thread(thread_id) -> bool
```
Plain dicts; short-lived sessions.

### Phase 1 — persist turns (`api/routers/chat.py`)
For the **library-wide** path only (skip when `item_id` is set — Reader stays
ephemeral):
- Read `thread_id` from the body; if absent, `create_thread()` and remember it.
- Persist the **user** message (the inbound parts) before/around starting the stream.
- In `on_complete(result)`, persist the **assistant** message from the emitted
  parts (or reconstruct from `result` per the spike outcome). Persistence is
  **fire-and-forget relative to the token stream** — a failed write logs and
  continues; it must never kill the answer.
- Emit a `data-thread-id` part on the first turn so the client learns the new id.

### Phase 2 — parallel title generation
When a brand-new thread's first turn begins:
```python
title_task = asyncio.create_task(_generate_title(first_user_text))
```
Run it **concurrently** with `dispatch_request`. `_generate_title` is one cheap
`build_chat_model()` (or a smaller model) call: "Title this conversation in ≤6
words, no quotes." In `on_complete`:
- if `title_task` is done → `set_title(...)` and emit a `data-thread-title` part;
- else → leave NULL; client falls back to the first message preview and picks up
  the title on the next `list_threads` fetch (or `await` with a short timeout).
Never block the answer stream on the title.

### Phase 3 — read/CRUD endpoints
| Method & path | Service |
|---|---|
| `GET /api/chat/threads` | `list_threads` |
| `GET /api/chat/threads/{id}` | `get_thread` (404 if missing) |
| `PATCH /api/chat/threads/{id}` | `rename_thread` (`{title}`) |
| `DELETE /api/chat/threads/{id}` | `delete_thread` (204) |
`api/schemas.py`: `ChatThreadSummary`, `ChatThreadDetail`.

### Phase 4 — frontend
- `lib/queryKeys.ts`: `chatThreads()`, `chatThread(id)`.
- Hooks: `useChatThreads()` (list), mutations for rename/delete (invalidate list).
- `useAgentChat.ts`: accept `initialMessages` + `threadId`; send `threadId` in the
  per-message `body` (alongside `filters`); on receiving `data-thread-id`/
  `data-thread-title`, update local state + invalidate `chatThreads()`.
- `routes/chat.tsx`: a **thread sidebar** (list, sorted by `updated_at`; rename/
  delete); **open** = fetch `get_thread` → seed `useChat({ messages })`; **New
  chat** = fresh id, empty messages (thread row created lazily on first turn so no
  empty threads); sync the active id to `?thread=<id>` (client-nav — mind the SPA
  deep-route caveat in `CLAUDE.md`).

### Phase 5 — polish
LLM-title fallbacks, empty-thread cleanup, optional "delete all", history-cap on
replay (§7).

## 6. Wire additions
```jsonc
{ "type": "data-thread-id",    "data": { "id": "…" } }   // first turn of a new thread
{ "type": "data-thread-title", "data": { "title": "…" } } // when the title call returns
```

## 7. Gotchas
- **Persist parts, not text** — flattening loses tool traces, reasoning, citations.
- **Continuation invariant:** replayed history must keep each `tool-call` with its
  `tool-result` (one reply per `tool_call_id`). The spike (§3) validates this; the
  history cap must trim by **whole turns**, never mid-tool-exchange.
- **History cap:** persisted threads grow unbounded — cap what's *replayed to the
  model* (by whole turns) even though the full thread is stored/shown. (Already
  flagged in `AGENTIC_CHAT_PLAN.md`.)
- **Never block streaming on DB writes or the title call** — both are async/
  best-effort around the stream.
- **Aborted/errored turns:** persist whatever parts exist at `on_complete`; skip if
  empty.
- **Empty threads:** create the row lazily on first successful turn.
- **Reader path:** early-return before any thread logic for `item_id` requests.
- **Tool-output bloat:** tool results can quote large transcript chunks; storing
  them verbatim bloats rows. Consider truncating stored tool-output parts while
  keeping answer text + citations full.
- **Single user** → no locking needed; `seq` + `updated_at` ordering suffices.

## 8. Test plan
- `chat_history` CRUD against the temp DB (create/append/list/get/rename/delete,
  cascade).
- **Persistence**: scripted `FunctionModel` turn through `/api/chat` with a
  `thread_id`; assert a thread + user row + assistant row (with parts) exist; assert
  `data-thread-id` emitted on first turn.
- **Continuation**: seed a second turn with the stored history; assert it streams
  and (spike-dependent) the model receives prior context.
- **Title**: monkeypatch `_generate_title` to a known string; assert `set_title`
  ran and `data-thread-title` emitted.
- **Reader path**: `item_id` request creates **no** thread.

## 9. Acceptance criteria
- Send messages, reload, reopen from the sidebar → the thread renders with its tool
  traces + citations and you can **keep chatting** with context.
- New threads get an auto title shortly after the first turn, without delaying the
  first answer.
- Reader item-chat remains ephemeral (no threads created).

## 10. Effort
**Medium** (+ a short spike). Migration + CRUD service + 4 endpoints + persistence
in `on_complete` + parallel title task + a sidebar and `useChat` seeding. The spike
(§3) is the gate; everything after it is conventional.
